## 5. P1：2.7 知识点依据与维护边界

### 5.1 数据契约

建议新增 `plugins/kaoyan-408/references/kp-408.json`。顶层包含 `schemaVersion` 与 `knowledgePoints`，每个条目至少包含：

| 字段 | 约束与含义 |
| --- | --- |
| `id` | 稳定且唯一的项目内部标识，例如 `OS-MEM-001`；不是官方大纲编号 |
| `subject` / `name` | 408 四科之一及知识点名称 |
| `syllabusPath` | 大纲条目路径；未知时为 `null`，自拟分类不能冒充官方原文 |
| `basisYear` | 必填，四位年份字符串或字面量 `待核` |
| `verified` | 默认 `false`；仅指该知识点与指定年度大纲的映射核验状态 |
| `source` | 未核时可为 `null`；已核时包含来源标题、URL 或文件标识、可定位的条目 |
| `checkedAt` | 已核时记录核验日期，否则为 `null` |

`verified: true` 必须同时有确定年份、已实际阅读的权威大纲原文、定位信息和核验日期。`basisYear: "待核"` 不能搭配 `verified: true`。网页标题、搜索摘要或旧年大纲不能替代指定年度原文。

2.7 不填教材章节、教材页码，也不批量把条目标成已核。这里只建立知识点归属证据，不声称大纲证明了公式、解法或用户答题正确。公式适用条件和计算复核仍在题目解释中分别说明。

### 5.2 内容与学习输出

先按四科各约 15 条安排编辑量，再按真实题目需要调整，共约 60 条。“高频”是首批编辑优先级，不伪装成统计得到的历年命题频率。优先覆盖现有三场景和脚本可验证的知识点。

只接入 `kaoyan-408-tutor` 与 `kaoyan-error-loop-coach` 中的 408 任务；数学、英语、政治不强塞 408 标签。每题反馈增加简短依据块，示例：

> 【知识点依据】OS-MEM-001｜操作系统·页面置换（项目分类）｜大纲年度：待核｜状态：待核。当前依据为题面条件与 FIFO 规则；本条尚未核对年度大纲原文。

这是格式示例，不是已完成核验的知识点条目。实际输出有已核来源时显示年度、原文定位及来源；未收录时明确“未收录/待核”，内部匹配值可为空，不虚构 ID，不硬套最接近的条目。

用户只要提示或处于独立作答阶段时，若精确知识点会泄露答案，先保留宽泛主题；最终讲评再补逐题详细依据。没有用户解题过程时，仍只能指出“最早易错点”，不能凭空诊断个人错误。

复用现有计算脚本：Cache、FIFO/LRU、FCFS/RR。其他计算题采用明确标注的人工复核；不因新增依据块就承诺所有题型有确定性计算器。

### 5.3 去重说明与使用记录

当前仓库新增维护边界说明，列固定比较提交、同名清单和正文分叉状态，建议避免同时启用同名技能。说明 408 仓库接下来重点维护的三类学习场景，并保留现有 2.x 能力。不宣布已移除重复技能，不自动删除另一仓库内容。另一仓库的 README 修改另列后续任务。

以私有、人工自用记录辅助决策，记录日期、客户端版本、请求类型、预期/实际 Skill、依据缺口和是否解决问题；不默认上传原始对话，不加遥测。收集约两周即可与验收失败、GitHub issues 一起评估 3.0。

### 5.4 文件与验收

主要文件：新增知识点 JSON 和对应结构校验；修改两个 Skill、必要共享契约、`scripts/release_payload.py`、`scripts/validate_repository.py` 及相关测试；添加维护边界说明和评测样本。

验收包含：约 60 条全部人工内容审阅；ID 唯一、年度和状态约束、来源定位完整性；至少 12 道覆盖四科的代表题及未收录、待核、跨科、仅提示等边界案例。逐题判断映射是否合理，不能只有字符串存在测试。记录已核与待核数量，不以 100% 已核作为造假的诱因。

最终发布候选运行完整工程门禁，并按新插件树重生成官方验证器证据和产物；行为记录绑定新树。开发阶段仅运行受影响检查，不为每次文案修改反复运行整套测试。

## 6. P2：2.8 版本、客户端和路由验证

### 6.1 版本单源

使用 `plugins/kaoyan-408/.codex-plugin/plugin.json` 的 `version` 作为 2.x 唯一版本源，不另立 `plugin.meta.json` 或 `skillset.json`。

生成器同步五处现有消费者：插件内 ZCode/CodeBuddy 清单、根 Cursor 清单、根 Claude/CodeBuddy marketplace 的插件版本。新增 Claude 原生清单后纳入派生；`.agents/plugins/marketplace.json` 当前没有版本字段，不无故新增。

提供只读 `--check` 模式，派生结果不同则退出失败；普通生成只修改已定义字段，保留宿主特有字段。保留独立字段校验和变异测试，避免生成器与校验器复制同一个错误。

`tests/system-validator-evidence.json` 必须由真实验证生成，不由版本脚本改写。CodeBuddy marketplace 的 `metadata.version: "1.0.0"` 是独立市场级字段，含义须按宿主约定确认，不能强制同步成插件版本。README 历史发布版本也不做全局替换。

### 6.2 Claude Code 与真实平台支持表

先做小范围兼容验证：检查 ZCode 与 Claude Code 能接受的 marketplace 字段交集，补插件内 Claude 原生清单，再在两端真实加载。若共享入口不兼容，依据实际发现规则生成单独分发根目录；不能随意改成客户端不认识的文件名，也不能破坏已有 ZCode 安装路径。

支持表按具体产品记录：Codex CLI、实际测试的 Codex 桌面端、Claude Code、Cursor、ZCode、WorkBuddy。没有测试的产品保留“未测”，Codex CLI 通过不能自动扩展为所有 Codex 产品通过。

每行至少记录：客户端版本、系统、日期、源码提交/插件树、安装入口、14 个 Skill 发现结果、引用可达、脚本调用与守卫限制、实际行为抽查结果及证据路径。状态区分“结构校验通过”“安装实测通过”“行为抽查通过”；不能压缩成一个含义不明的“支持”。

每个可用客户端先完成安装、发现、读取共享引用，以及代表性脚本调用/降级冒烟。Mimosa 拒绝脚本时如实记录受限，不绕过守卫，不称完整确定性能力可用。已有 health check 优先复用，仅针对新布局补缺口。

Claude Code 无法获得真实测试环境时，Claude 支持任务保持未完成；若决定先拆出其他成果发布，应明确缩小版本目标，不能以静态 schema 替代安装验收。

### 6.3 十组容易混淆的请求

至少 10 组 A/B 请求，即至少 20 个自然输入，另补必要的多轮上下文。优先在 Codex 做可复现路由验收；其他宿主的安装抽查不能替代这组路由证据。

| 组 | A/B 对照重点 |
| --- | --- |
| 1 | 单题第一处错误 / 多题错因聚类 |
| 2 | 制定周计划 / 执行当前 90 分钟任务 |
| 3 | 根据进度快照诊断 / 从目标重新制定计划 |
| 4 | 核一个官方事实 / 完整院校招生研究 |
| 5 | 查找真题来源 / 分析已提供的真题样本 |
| 6 | 概念“为什么” / 数值与计算过程校验（可同属 tutor，不同输出要求） |
| 7 | 讲解已给题面 / 核验题目出处 |
| 8 | 只给提示 / 完整答案与讲解 |
| 9 | 所有笔记只读 / 仅禁用 Notion（使用隔离夹具，不写真实用户笔记） |
| 10 | 延续上一题 / 明确换题换科，补复合任务上下文 |

测试模型只看到自然请求与正常技能发现环境，不能提前看到预期 Skill、知识点 ID 或答案。现有 `eval/v2.6-acceptance/run_cases.py` 会提供指定 Skill，因此不能原样用于证明自动路由正确。

评分侧另存预期主责、允许的澄清、行为约束；记录实际发现/调用轨迹、误接、漏接、提示泄题及依据错误。区分路由通过率与讲解正确性；修复后重测相关失败和必要回归，不用少量样本宣称全局准确率。

主要文件：清单生成脚本与独立校验测试、宿主清单、README/平台支持表、隔离安装证据、路由评测输入与评分记录。具体路径在实施时沿用现有目录约定，避免搭建第二套完整测试框架。
